# Crow Bot: repository guidance

## Product

Crow Bot gives a person or a team AI teammates, called bots. Each bot has its own computer, works without supervision, and learns from use. Personal use on the user's own computer is free. Revenue comes from hosted servers and from licenses for use at work.

Distribution waits for the product. Until Crow Bot works as its owner intends on its target systems, no plan or PRD prepares a release: no package, installer, release build, store listing, or domain. Work that serves a build from source (a desktop entry, a systemd unit installed by a script of the repository) is not distribution.

## Architecture

- **Daemon (`crowbotd`)**: a headless Rust binary. It owns bots, conversations, memory, skills, and storage. It runs on the user's computer or on a Linux server, as one binary with no display. It listens on a local endpoint: a named pipe on Windows, a Unix socket elsewhere. Each conversation is one task (`conversation.rs`) that records events, sends them to the attached clients, and holds the pending approvals and the queue of messages sent during a turn. At start the daemon locks the file `<db>.lock` for its whole life (`instance.rs`), opens the database, ends every turn that a previous daemon left running (`Store::recover`), and claims its endpoint last: an endpoint that answers belongs to a daemon that is ready, and a daemon that fails to start is never reached. A second daemon on the same database, on any endpoint, exits with status 3 before it opens it, and one whose endpoint another program holds exits with status 4 (`EXIT_DATABASE_HELD`, `EXIT_ENDPOINT_HELD` in the protocol crate); `<db>.owner` names the daemon that holds the lock, for that message only. The agents it starts end with it, even when it is killed (`lifetime.rs`): on Windows the daemon puts itself in a job object that kills its processes when it ends, which a sign-in leaves so that the browser it opens stays; on Unix each agent runs under a guard, the daemon's own program with `--guard-agent`, that kills the agent's process group once the daemon is gone: the guard blocks on the read end of a pipe whose write end only the daemon holds, so it learns of the daemon's end at once, with no timer. SIGTERM, SIGINT, and SIGHUP stop the daemon cleanly (`stop.rs`): it lets go of its endpoint, which removes the socket, stops every turn (waiting approvals answered as cancelled, an agent still running after 3 seconds closed), sends `Stopping` to each client, closes the database, and exits 0 within 5 seconds; a second signal ends it at once.
- **Folders and files.** On Linux the defaults follow XDG (`Folders` in the protocol crate, which the client and the daemon both read): the database, the runtimes, and the provider homes under `$XDG_DATA_HOME/crowbot`, the client's log of a daemon it started under `$XDG_STATE_HOME/crowbot`, and the socket under `$XDG_RUNTIME_DIR/crowbot`; elsewhere all of them stay in `~/.crowbot`. The bots folder is `~/CrowBot/Bots` everywhere. A socket path over `SOCKET_PATH_LIMIT` makes the daemon exit with status 5 (`EXIT_ENDPOINT_TOO_LONG`) before it creates anything. On Unix every folder the daemon creates is 0700 and every file of its own 0600, whatever the umask (`private.rs`); the umask itself is left alone, because the agents write the user's files with it. A database folder of another account is refused.
- **Supervision on Linux.** The systemd user unit `crates/crowbotd/resources/linux/systemd/crowbotd.service` (`Type=notify`, restart on failure, `KillMode=mixed`: a stop signals the daemon alone, which ends its turns and agents itself, then systemd kills whatever is left in the unit) is installed and enabled by `scripts/desktop-files.sh`. The daemon writes `READY=1` to `NOTIFY_SOCKET` itself once its endpoint is claimed (`systemd.rs`, no library). The client starts the unit through `systemctl` when it is installed and the client runs the default daemon (`service.rs`); with `--endpoint`, `--daemon`, or daemon arguments, or with no unit or no systemd, it starts the daemon detached in a session of its own. The client never turns lingering on; the daemon reports it in `DaemonInfo`, and Settings > About shows the command when it is off.
- **Bots**: a bot is a record (`store/bots.rs`) with a name, an avatar (a color and a head: the mascot the client draws), instructions, a folder, a provider, a model, a reasoning level, and a permission level. It owns its conversations, and one of them is its current one: the one a client shows when the bot is opened. `daemon.rs` holds what connections and conversations share: the attached clients, the running conversations, and the state of each bot (working, waiting, failed, unread), which it sends to every attached client when it changes. A bot created with no folder gets one under `--bots-dir` (`~/CrowBot/Bots`); the daemon never deletes a bot's folder.
- **Desktop client (`crates/crowbot-desktop`, binary `crowbot`)**: Rust with GPUI. It is a thin client: it attaches to a daemon through one protocol, local or remote, and holds no durable state. It rebuilds what it shows from the snapshot the daemon sends when a conversation opens. When no daemon listens, it starts `crowbotd` from the folder of its own executable as a detached process that outlives it (`connection.rs`).
- **Protocol crate (`crates/crowbot-protocol`)**: written in this repository and shared by the daemon and the client. One JSON message per line, after a `hello` that carries `PROTOCOL_VERSION`. It owns the `Event` type, and its `transport` feature holds the local listener and connector.
- **Two Cargo workspaces.** The root workspace holds `crowbotd` and `crowbot-protocol`. `crates/crowbot-desktop` is its own workspace, with its own `Cargo.lock`, and takes the protocol crate by path. Run Cargo for the client from `crates/crowbot-desktop` or with `--manifest-path`. The split keeps Zed's dependency patches and GPUI's dependency versions out of the daemon.
- **Providers**: Claude, ChatGPT (provider id `codex`), and Grok. The daemon starts each one through the Agent Client Protocol (ACP): `claude-agent-acp`, `codex-acp`, and the `grok` CLI. One profile per provider (`provider/claude.rs`, `codex.rs`, `grok.rs`) holds what differs: arguments, environment, the session mode that asks first, and the sign-in. Grok opens no browser for a sign-in over ACP: the daemon asks it for the page and passes the address to the clients, and the window that started the sign-in opens it (`docs/provider-sign-in.md`). `daemon/providers.rs` holds the state of each provider, its sign-ins, and the models and reasoning levels it reports, which are never hard-coded. A bot that moves to another provider keeps its conversation: the first turn there gets a handoff built from the stored events (`handoff.rs`, 50,000 characters at most), and each provider keeps its own session per conversation (`store/sessions.rs`).
- **Managed runtimes** (`runtime.rs`, `runtime/pins.rs`): the daemon downloads the agent of a provider at the first turn that needs it, at a pinned version, and checks each file against a pinned SHA-256 before anything of it runs. The marker of an installed runtime (`installed.json`) holds the SHA-256 of each file it unpacked, and the daemon reads the whole folder again before each start of the runtime: a file changed, removed, or added makes it not installed, and the next turn downloads it again. The check finds a runtime that changed after its install; it is not a boundary against a process that writes as the user, which could rewrite the marker too, or change a file between the check and the start. That boundary is the approvals. An install holds the lock file `<provider>/<version>.lock`, so two daemons that share `--data-dir` download a runtime once. Runtimes live under `<data>/runtimes/<provider>/<version>/`, where `<data>` is `--data-dir` or the folder of the database. `--runtime-manifest <file.json>` replaces the pins (tests, mirrors). The program of a provider is, in this order: the `--agent` command, the executable the user set for that provider, the installed runtime, a download. No Bun or Node.js is needed on the computer.
- **Memory, skills, and learning** live in the daemon. The daemon serves them to provider CLIs through MCP.

## Hard rules

- **License boundary.** Each crate carries its own license file. The desktop client is GPL-3.0-or-later, so it may depend on Zed's GPL crates and adapt Zed's GPL code. The protocol crate is Apache-2.0, because both the GPL client and the daemon link it. The daemon is PolyForm Noncommercial 1.0.0. The daemon and the protocol crate must not depend on any GPL crate.
- **Model usage belongs to the user.** A bot runs on the user's own subscription or API key. Never pay for, resell, or proxy model usage. Never read, copy, or store provider credentials: sign-in happens in the provider's own CLI. Run provider binaries unmodified.
- **The daemon owns approvals.** A bot must not inherit what its owner allowed for personal use. The Claude profile (`provider/claude.rs`) starts each session with `settingSources: []`, refuses bypass mode, and sets the session mode to `default`, so every gated tool call reaches the daemon as an approval request. Codex and Grok each run in a home the daemon owns (`<data>/providers/<id>/home`), so the user's own settings, rules, hooks, and servers do not reach a bot: Codex in the session mode `read-only` with a `config.toml` the daemon rewrites before each start, which trusts no folder (so the `.codex` config of a bot's folder does not apply), and with no hooks, rules, plugins, skills, instructions, or memories left in its home, Grok with `--permission-mode default`, a `config.toml` the daemon rewrites before each start, and no trusted folders, hooks, workflows, language servers, plugins, skills, or memories left in its home (Grok reports no session mode over ACP, so that argument sets it). A turn fails, naming the provider and the mode, when the agent does not offer the mode that asks first. When an agent reports that it moved out of that mode on its own, the daemon stops the turn and closes the session (`provider/acp.rs`). A request waits until a client answers it, and the daemon only ever selects the allow-once or the reject-once option: it declines a request that offers no allow-once option. A stopped turn answers its waiting requests as cancelled, after the cancel itself. For a bot on Full access the daemon selects the allow-once option itself and records why (`ApprovalReason`). The permission level is read from the bot's record at each request (`conversation.rs`) and from nowhere else: no prompt, tool result, or file can change it.
- **A provider session follows the bot's settings.** The provider, the instructions, the model, the reasoning level, and the folder of a bot form a revision (`bots.session_revision`): a change closes the live session. A stored session (`provider_sessions`, one per conversation and provider) is resumed only when its fingerprint, a hash of the instructions, the model, the reasoning level, and the folder, matches the bot's; otherwise the next turn starts a new session, and the history stays in the database. So a bot that goes back to a provider with the same settings resumes the session it had there. Instructions go to the agent as the ACP `systemPrompt` when it advertises that capability, and at the start of the first prompt otherwise (`provider/acp.rs`).
- **The database is the source of truth.** A conversation is the ordered list of its events in SQLite (`store.rs`). The provider session is only a handle to resume the agent; the daemon never reads history back from a provider. Schema changes go through `PRAGMA user_version`, keep all user data, and a daemon refuses a database that a newer daemon wrote. All pending schema steps run in one transaction: a failure leaves the database at the version it had. A stored event is the JSON of the protocol `Event`, so a change to `Event` must still read the rows already stored: add fields with `#[serde(default)]`, never rename or remove a variant.
- **The endpoint belongs to one user.** The Windows pipe is created as the first instance of its name, owned by the account of the daemon, with an access list that holds only that account. Before it sends anything, the client checks that the pipe it opened has its own account as owner and that the pipe's server process runs as that account (`transport/windows.rs`). The owner check is the one that holds against an impostor: a pipe reports the process id of its creator, and that id can be reused. The Unix socket is readable and writable by its owner only, in a folder only its owner may enter, and the daemon drops a connection from another user; the client checks that the daemon runs as its own account before it sends anything, and a stale socket file is removed only by the holder of the lock file `<socket>.lock`, so two daemons that start at once cannot remove each other's socket (`transport/unix.rs`).
- **ACP stays at the edge.** ACP types do not leave the provider adapter. Inside, the daemon records its own events (message, tool call, approval request).
- **GPUI source.** GPUI comes from Zed's git repository at a pinned rev, with Zed's `[patch.crates-io]` entries. Never use the crates.io `gpui`. The rev and the patches live in `crates/crowbot-desktop/Cargo.toml`; when the rev changes, copy the patch entries from Zed's `Cargo.toml` at that rev. One exception, for what GPUI cannot do on Linux: the client takes Zed's `gpui_wgpu` at the same rev from `crates/crowbot-desktop/patches/gpui_wgpu`, through a `[patch."https://github.com/zed-industries/zed"]` entry, with the changes recorded in `patches/gpui_wgpu.diff` (COLRv1 emoji, fallback families with no Latin glyph, emoji presentation). Only Linux builds that crate. Change GPUI there and nowhere else; after a change run `sh scripts/gpui-patches.sh diff`, after a rev bump `sh scripts/gpui-patches.sh refresh`, and `sh scripts/gpui-patches.sh check` must pass. `crates/crowbot-desktop/patches/README.md` says what each change does and where it stands upstream; a change Zed takes leaves the diff at the next rev bump. Any other GPUI defect is handled in the client, not by patching another GPUI crate (as `truncated.rs` does for a truncation that splits graphemes and `reduced_motion.rs` for the system's reduced motion).
- **Design contract.** UI work in the desktop client follows `DESIGN.md`: its tokens, its geometry rules (concentric radii; GPUI clips to rectangles, so no fill may reach a rounded corner), and its component contracts. A visual change that departs from it updates it in the same commit.
- **Visual checks and desktop control.** To look at the running client (a visual pass, a screenshot of a state) or to take control of the computer (click, type, drive a window), use the `/agent-desktop` skill. Do not use another automation tool for it. Never start or drive OpenBot with it: doing so started many processes and crashed the computer. Compare against screenshots of OpenBot that Arthur provides, and ask before the skill is used again in a session where he stopped it.
- **Reference projects.** OpenBot, Hermes Agent, and Zed are references for ideas: read them to learn how a problem was solved, then design the answer for this codebase. Never copy or translate OpenBot code or text; its license is noncommercial.

## Open decisions

- Full isolation of a bot from the user's `~/.claude`. The Claude profile already ignores the user's settings and instructions, but the bot still signs in with the user's credentials and writes its transcripts there. A daemon-owned `CLAUDE_CONFIG_DIR` would isolate both, at the price of one more sign-in. Codex and Grok already run that way: the user signs in to each once from Crow Bot.
- The Codex session mode. `read-only` is the only mode of `codex-acp` in which every write asks first; its sandbox also keeps shell commands from writing. Whether a bot on Full access should run Codex in a wider mode is not decided.
- The remote transport. The protocol runs over any byte stream, but only the local endpoint exists: encryption and client sign-in for a daemon on a server are not designed.
- The Unix side of the endpoint is verified on Linux only. macOS is not verified.
- The transitions of the bot mascot. The mascot is drawn and alive (`DESIGN.md` 5.12): a crow's head seen from the front, in the bot's color, alone with no disc or background behind it, with a head the user picks, one beak for all, and eyes that show the bot's state. Its head sways, its eyes blink, and the dots of a bot that works hop; that state has no badge, and the states that ask for the user (waiting, failed, unread) keep theirs. The eyes change at once from a state to the next: that transition is not designed.
- Whether a native Rust client for the Claude CLI replaces `claude-agent-acp` later. If it does, it plugs in as an ACP agent, so the daemon does not change.
