# Crow Bot: repository guidance

## Product

Crow Bot gives a person or a team AI teammates, called bots. Each bot has its own computer, works without supervision, and learns from use. Personal use on the user's own computer is free. Revenue comes from hosted servers and from licenses for use at work.

Distribution waits for the product. Until Crow Bot works as its owner intends on its target systems, no plan or PRD prepares a release: no package, installer, release build, store listing, or domain. Work that serves a build from source (a desktop entry, a systemd unit installed by a script of the repository) is not distribution.

## Architecture

- **Daemon (`crowbotd`)**: a headless Rust binary. It owns bots, conversations, memory, skills, and storage. It runs on the user's computer or on a Linux server, as one binary with no display. It listens on a local endpoint: a named pipe on Windows, a Unix socket elsewhere. Each conversation is one task (`conversation.rs`) that records events, sends them to the attached clients, and holds the pending approvals and the queue of messages sent during a turn. At start the daemon locks the file `<db>.lock` for its whole life (`instance.rs`), opens the database, ends every turn that a previous daemon left running (`Store::recover`), and claims its endpoint last: an endpoint that answers belongs to a daemon that is ready, and a daemon that fails to start is never reached. A second daemon on the same database, on any endpoint, exits with status 3 before it opens it, and one whose endpoint another program holds exits with status 4 (`EXIT_DATABASE_HELD`, `EXIT_ENDPOINT_HELD` in the protocol crate); `<db>.owner` names the daemon that holds the lock, for that message only. The agents it starts end with it, even when it is killed (`lifetime.rs`): on Windows the daemon puts itself in a job object that kills its processes when it ends, which a sign-in leaves so that the browser it opens stays; on Unix each agent runs under a guard, the daemon's own program with `--guard-agent`, that kills the agent's process group once the daemon is gone: the guard blocks on the read end of a pipe whose write end only the daemon holds, so it learns of the daemon's end at once, with no timer. SIGTERM, SIGINT, and SIGHUP stop the daemon cleanly (`stop.rs`): it lets go of its endpoint, which removes the socket, stops every turn (waiting approvals answered as cancelled, an agent still running after 3 seconds closed), sends `Stopping` to each client, closes the database, and exits 0 within 5 seconds; a second signal ends it at once.
- **Folders and files.** On Linux the defaults follow XDG (`Folders` in the protocol crate, which the client and the daemon both read): the database, the runtimes, and the provider homes under `$XDG_DATA_HOME/crowbot`, the client's log of a daemon it started under `$XDG_STATE_HOME/crowbot`, and the socket under `$XDG_RUNTIME_DIR/crowbot`; elsewhere all of them stay in `~/.crowbot`. The bots folder is `~/CrowBot/Bots` everywhere. A socket path over `SOCKET_PATH_LIMIT` makes the daemon exit with status 5 (`EXIT_ENDPOINT_TOO_LONG`) before it creates anything. On Unix every folder the daemon creates is 0700 and every file of its own 0600, whatever the umask (`private.rs`); the umask itself is left alone, because the agents write the user's files with it. A database folder of another account is refused.
- **Supervision on Linux.** The systemd user unit `crates/crowbotd/resources/linux/systemd/crowbotd.service` (`Type=notify`, restart on failure, `KillMode=mixed`: a stop signals the daemon alone, which ends its turns and agents itself, then systemd kills whatever is left in the unit) is installed and enabled by `scripts/desktop-files.sh`. The daemon writes `READY=1` to `NOTIFY_SOCKET` itself once its endpoint is claimed (`systemd.rs`, no library). The client starts the unit through `systemctl` when it is installed and the client runs the default daemon (`service.rs`); with `--endpoint`, `--daemon`, or daemon arguments, or with no unit or no systemd, it starts the daemon detached in a session of its own. The client never turns lingering on; the daemon reports it in `DaemonInfo`, and Settings > About shows the command when it is off.
- **Bots**: a bot is a record (`store/bots.rs`) with a name, an avatar (a color and a head: the mascot the client draws), instructions, a folder, a provider, a model, a reasoning level, and a permission level. It owns its conversations, and one of them is its current one: the one a client shows when the bot is opened. `daemon.rs` holds what connections and conversations share: the attached clients, the running conversations, and the state of each bot (working, waiting, failed, unread), which it sends to every attached client when it changes. A bot created with no folder gets one under `--bots-dir` (`~/CrowBot/Bots`); the daemon never deletes a bot's folder.
- **Desktop client (`crates/crowbot-desktop`, binary `crowbot`)**: Rust with GPUI. It is a thin client: it attaches to a daemon through one protocol, local or remote, and holds no durable state. It rebuilds what it shows from the snapshot the daemon sends when a conversation opens. When no daemon listens, it starts `crowbotd` from the folder of its own executable as a detached process that outlives it (`connection.rs`).
- **Protocol crate (`crates/crowbot-protocol`)**: written in this repository and shared by the daemon and the client. One JSON message per line, after a `hello` that carries `PROTOCOL_VERSION`. It owns the `Event` type, and its `transport` feature holds the local listener and connector.
- **Two Cargo workspaces.** The root workspace holds `crowbotd` and `crowbot-protocol`. `crates/crowbot-desktop` is its own workspace, with its own `Cargo.lock`, and takes the protocol crate by path. Run Cargo for the client from `crates/crowbot-desktop` or with `--manifest-path`. The split keeps Zed's dependency patches and GPUI's dependency versions out of the daemon.
- **Providers**: Claude, ChatGPT (provider id `codex`), and Grok. The daemon starts each one through the Agent Client Protocol (ACP): `claude-agent-acp`, `codex-acp`, and the `grok` CLI. One profile per provider (`provider/claude.rs`, `codex.rs`, `grok.rs`) holds what differs: arguments, environment, the session mode that asks first, and the sign-in. Grok opens no browser for a sign-in over ACP: the daemon asks it for the page and passes the address to the clients, and the window that started the sign-in opens it (`docs/provider-sign-in.md`). On Linux every sign-in goes that way: its `BROWSER` and the first `xdg-open` on its `PATH` are the daemon's own program (`sign_in_page.rs`), which opens nothing and passes the page to the daemon over an abstract socket of that sign-in, so that no browser starts in the process group a cancel kills and a daemon with no display still shows the page. Before each Codex session on Linux the daemon starts the `bwrap` Codex picks once (`codex::check_sandbox`): a computer that disables user namespaces fails the turn with that cause. `daemon/providers.rs` holds the state of each provider, its sign-ins, and the models and reasoning levels it reports, which are never hard-coded. A bot that moves to another provider keeps its conversation: the first turn there gets a handoff built from the stored events (`handoff.rs`, 50,000 characters at most), and each provider keeps its own session per conversation (`store/sessions.rs`).
- **Managed runtimes** (`runtime.rs`, `runtime/pins.rs`): the daemon downloads the agent of a provider at the first turn that needs it, at a pinned version, and checks each file against a pinned SHA-256 before anything of it runs. The marker of an installed runtime (`installed.json`) holds the SHA-256 of each file it unpacked, and the daemon reads the whole folder again before each start of the runtime: a file changed, removed, or added makes it not installed, and the next turn downloads it again. The check finds a runtime that changed after its install; it is not a boundary against a process that writes as the user, which could rewrite the marker too, or change a file between the check and the start. That boundary is the approvals. An install holds the lock file `<provider>/<version>.lock`, so two daemons that share `--data-dir` download a runtime once. Runtimes live under `<data>/runtimes/<provider>/<version>/`, where `<data>` is `--data-dir` or the folder of the database. `--runtime-manifest <file.json>` replaces the pins (tests, mirrors). The program of a provider is, in this order: the `--agent` command, the executable the user set for that provider, the installed runtime, a download. No Bun or Node.js is needed on the computer. A folder of runtimes on a file system mounted `noexec` is refused before any download, and a program with no execute bit is reported as not found, with the missing permission named.
- **Tests and continuous integration.** A test makes its folders with `crowbot_protocol::scratch::Scratch` (the dev-only feature `scratch`): the folder sits where a socket inside it fits, whatever `TMPDIR` is, and is removed when dropped, so a run leaves nothing in `/tmp`. A test that root cannot run says so with `support::skipped_as_root`, since a container job runs as root. `.github/workflows/ci.yml` runs the six gates with `--locked` on Fedora 45 (a container job) and Ubuntu 24.04, each on x86_64 and arm64, and on Windows Server 2025 (x86_64), each gate a step of its own; on Fedora `scripts/window-test.sh` then opens the real client on a headless Mutter and on Xvfb, and must fail on a client built with `--no-default-features`, which holds no display backend. `scripts/stress-tests.sh` runs the daemon tests 24 at once, 20 times.
- **The harness** (memory, skills, learning, routines, checkpoints, delegation, goals) is specified in `tasks/prd-crow-bot-harness.md`. It lives in the daemon, which serves it to the provider agents as MCP tools through a bridge, its own program with `--mcp-bridge`, that relays to an endpoint of that session. Its channel is built (EP-001): each provider session gets an endpoint of its own (`mcp.rs`: an abstract socket on Linux, a pipe only the account may open on Windows), whose bot and conversation every call comes from, and the session's `mcp_servers` names the bridge to it; the bridge holds no logic and exits when the endpoint closes (`mcp/bridge.rs`). The MCP server is written here (JSON-RPC with `initialize`, `tools/list`, `tools/call`). Each tool has a typed input whose JSON schema the agent reads and one effect fixed in its type (`tools.rs`); a result over `TOOL_OUTPUT_BYTES` comes as a preview with a cursor for `read_output`. The system prompt is the instructions, then the registered sections by rank (`prompt.rs`), frozen when the session opens; a later change travels in a note before the person's text, stored in the `UserText` it came with, and the versions each provider session saw are stored with it (`provider_sessions.sections`). How each provider names a call to a daemon tool is recorded in `docs/harness-providers.md`. Debug builds started with `CROWBOT_TEST_HARNESS` add test tools and sections (`test_harness.rs`). The guard of a turn is built (EP-002): every `UserText` records the origin of its turn (`TurnOrigin`, `User` for every message a client sends, whatever it names); what an agent reports a turn consumed (`UsageUpdate`, the tokens of the prompt response) is stored per turn in `turn_usage`, its cost as the growth of the session's cost, and a snapshot carries the usage of the last turn that ended; the daemon stops a turn that repeats one tool call or a cycle of 2 to 4 with the same title, input, and output five times (`NoProgress`), a turn of an origin other than `User` whose agent sent nothing for 600 seconds while no approval waits (`Inactive`), and a turn that starts more tool calls than the bot's `tool_call_limit` (`BudgetExhausted`), each recorded as the cause of its `TurnInterrupted`; a turn that failed for no named cause before any text or tool call is sent again as a `Retry` turn after 15, 30, then 60 seconds, a stop or a new message dropping the wait (`guard.rs`, the figures in `guard/limits.rs`, which the daemon's tests read too, and which debug builds divide by `CROWBOT_TEST_TIME_SCALE`). `PauseDaemon` writes the file `PAUSED` of the data folder and `ResumeDaemon` removes it: while it exists, at start too, the daemon starts no turn of an origin other than `User`, lets running turns end, and `DaemonInfo.paused` says so. Memory is built (EP-004): entries are rows of `memory`, each with a scope (`Bot`, or `User`, which every bot reads and which outlives the bot that wrote it), a `core` flag, its author, and the event that grounds it, never rewritten but retired, a correction adding an entry that names the one it retires (`store/memory.rs`); the `memory` tool applies a list of operations all or none, refuses a text the scan flags unless a person writes it, and holds the core entries of a scope within `CORE_MEMORY_BOT_CHARACTERS` or `CORE_MEMORY_USER_CHARACTERS`; the core entries are two sections of the system prompt, each entry on one line with its source event and unable to open or close the fence of recalled memory, an entry with a scan finding shown as a placeholder that names the category, sent again in the note when the context size an agent reports falls; the other entries are recalled by the words of each message, in a fence of the note (`memory.rs`). `scan.rs` is the one scan of text the daemon injects (categories, severities, a quotation lowering a finding to `Caution`), checked against `scan/fixture.json`. `session_search` reads a bot's other conversations, messages and tool calls, from the search index alone (`history.rs`). Clients read and change memory with `ListMemory`, `ChangeMemory`, and `Memory`; a person's change is recorded in the bot's current conversation. Skills are built (EP-005): each version is rows keyed by its hash, the SHA-256 of each file's path and hash, each file stored once by its SHA-256, a skill naming its active version, and a log of changes that nothing rewrites or removes (`store/skills.rs`); a version holds a `SKILL.md` whose front matter (read by the daemon, no YAML library) names the skill and describes it, and files only under `references`, `templates`, `scripts`, and `assets`, within the limits of `skill.rs` in the protocol crate (`skills/format.rs`). Before each session, and after each change, the daemon writes the active versions under `<data>/skills/<bot>/<skill>/`, files 0400 and folders 0500, and checks every file against its hash: a folder that differs is written again, and a skill that cannot be written is left out of that session's index with a `SkillUnavailable` event (`skills/projection.rs`). The index is a section of the system prompt, one line per active skill cut at `SKILL_INDEX_DESCRIPTION_CHARACTERS`, after the instruction to load a matching skill with `skill_view`; `skills_list` and `skill_view` read, and `skill_manage` (not in a delegated session) applies create, correct, write a file, remove a file, and archive all or none, each change of an existing skill naming the version the agent read; a version with a `Dangerous` finding waits for a person, whatever the level and the rules (`Mutation::for_person`, `Request::person`), and only a person archives a pinned skill (`skills.rs`). Clients read and change skills with `ListSkills`, `ListSkillHistory`, `RollBackSkill`, `ImportSkill` (refused with the findings unless confirmed), and `SetSkillState`, recorded in the bot's current conversation. Learning from use is built (EP-006; the curator, which spares the skills a routine names, comes with the routines in EP-007): what the daemon may start for a bot is its `HarnessSettings` (a switch per origin, `retry` alone on by default, a daily limit of turns that any other switch needs, an optional daily limit of tokens, and the verification reminder), stored as JSON in `harness_settings` and written only by `SetHarnessSettings`; every daemon-started turn passes `Daemon::admit`, under a lock held until its start is recorded (`Daemon::admission`), so that two turns cannot both take the last place of a day (`daemon/harness.rs`: not paused, its switch on, the turns and the reported tokens of the daemon's local day under the limits, the day read by SQLite in the computer's time zone), and one that does not start is a row of `turn_refusals`, told in its conversation as `TurnNotStarted` unless its switch is off; the origin of a started turn is the one its `UserText` records, so the ledger of started turns is the events, which `GetConsumption` sums per origin for the day. A turn stopped for `BudgetExhausted` starts at once, ahead of the queue, one turn of origin `Budget` that asks for a summary (`guard::BUDGET_SUMMARY`), when that switch allows it. A review (`review.rs`, figures in `review/limits.rs`) is a conversation of the bot with a row in `reviews`, started when a turn ends with no turn of the bot running, queued, or waiting to be sent again and 10 tool calls (since the last review of skills or the bot's last skill change) or 10 turns of a person (since the last review of memory or the bot's last memory change) ran in its other conversations, a review that a person stopped or that failed leaving its work to the next one; the daemon reserves a bot's review in the same section of its state that found no turn of the bot working, so a bot never has two and a person's turn that starts later stops it; its sessions are of kind `Review`, which lists no `External` tool, every request for an agent's own tool is declined as `ReviewSession`, it takes no message from a person and is not retried, a person's message to the bot stops it, and when it changed memory or a skill the conversation it reviewed records `ReviewApplied`. `skill_view` records the version it loaded for the turn (`SkillUses` in `tools.rs`); each turn that ended while the index listed a skill, or that loaded one, is a row of `skill_turns` with its end and the versions in `skill_uses`, which `GetSkillFigures` and `GetBotSkillFigures` join with `turn_usage`. The rest of the harness is not built yet. The daemon calls no model API and runs no agent loop: it serves tools, guards a turn from the events it records, and starts turns of its own under the user's switches. The harness is written against the daemon's own events and tools, never against a provider, so it does not depend on who owns the loop.

## Hard rules

- **License boundary.** Each crate carries its own license file. The desktop client is GPL-3.0-or-later, so it may depend on Zed's GPL crates and adapt Zed's GPL code. The protocol crate is Apache-2.0, because both the GPL client and the daemon link it. The daemon is PolyForm Noncommercial 1.0.0. The daemon and the protocol crate must not depend on any GPL crate.
- **Model usage belongs to the user.** A bot runs on the user's own subscription or API key. Never pay for, resell, or proxy model usage. Never read, copy, or store provider credentials: sign-in happens in the provider's own CLI. Run provider binaries unmodified.
- **The daemon owns approvals.** A bot must not inherit what its owner allowed for personal use. The Claude profile (`provider/claude.rs`) starts each session with `settingSources: []`, refuses bypass mode, and sets the session mode to `default`, so every gated tool call reaches the daemon as an approval request. Codex and Grok each run in a home the daemon owns (`<data>/providers/<id>/home`), so the user's own settings, rules, hooks, and servers do not reach a bot: Codex in the session mode `read-only` with a `config.toml` the daemon rewrites before each start, which trusts no folder (so the `.codex` config of a bot's folder does not apply), and with no hooks, rules, plugins, skills, instructions, or memories left in its home, Grok with `--permission-mode default`, a `config.toml` the daemon rewrites before each start, and no trusted folders, hooks, workflows, language servers, plugins, skills, or memories left in its home (Grok reports no session mode over ACP, so that argument sets it). A turn fails, naming the provider and the mode, when the agent does not offer the mode that asks first. When an agent reports that it moved out of that mode on its own, the daemon stops the turn and closes the session (`provider/acp.rs`). A request waits until a client answers it, and the daemon only ever selects the allow-once or the reject-once option: it declines a request that offers no allow-once option. A stopped turn answers its waiting requests as cancelled, after the cancel itself. For a bot on Full access the daemon selects the allow-once option itself and records why (`ApprovalReason`). The permission level is read from the bot's record at each request (`conversation.rs`) and from nowhere else: no prompt, tool result, or file can change it.
- **A provider session follows the bot's settings.** The provider, the instructions, the model, the reasoning level, and the folder of a bot form a revision (`bots.session_revision`): a change closes the live session. A stored session (`provider_sessions`, one per conversation and provider) is resumed only when its fingerprint, a hash of the instructions, the model, the reasoning level, and the folder, matches the bot's; otherwise the next turn starts a new session, and the history stays in the database. So a bot that goes back to a provider with the same settings resumes the session it had there. Instructions go to the agent as the ACP `systemPrompt` when it advertises that capability, and at the start of the first prompt otherwise (`provider/acp.rs`). What the harness adds to the system prompt (core memory, the skills index) is frozen when a session opens and stays out of the fingerprint: a later change travels in a note the daemon puts before the user's message and stores with that message.
- **The database is the source of truth.** A conversation is the ordered list of its events in SQLite (`store.rs`). The provider session is only a handle to resume the agent; the daemon never reads history back from a provider. Schema changes go through `PRAGMA user_version`, keep all user data, and a daemon refuses a database that a newer daemon wrote. The first step creates the tables of an empty database on its own; every later pending step and the version number run in one transaction: a failure leaves the database at the version it had. Memory entries and skill versions are rows, each skill version stored by its SHA-256; the skill files an agent reads are a read-only projection under `<data>/skills`, written and checked by hash before each session. A stored event is the JSON of the protocol `Event`, so a change to `Event` must still read the rows already stored: add fields with `#[serde(default)]`, never rename or remove a variant.
- **The endpoint belongs to one user.** The Windows pipe is created as the first instance of its name, owned by the account of the daemon, with an access list that holds only that account. Before it sends anything, the client checks that the pipe it opened has its own account as owner and that the pipe's server process runs as that account (`transport/windows.rs`). The owner check is the one that holds against an impostor: a pipe reports the process id of its creator, and that id can be reused. The Unix socket is readable and writable by its owner only, in a folder only its owner may enter, and the daemon drops a connection from another user; the client checks that the daemon runs as its own account before it sends anything, and a stale socket file is removed only by the holder of the lock file `<socket>.lock`, so two daemons that start at once cannot remove each other's socket (`transport/unix.rs`).
- **What answers an approval without a person.** Four sources, checked in this order, each recorded as the `ApprovalReason`: a built-in refusal floor, a rule of the bot (refuse before allow), a daemon tool, and the bot's Full access level. A person writes a rule through a client message; no daemon tool, prompt, or file adds one. An allow rule matches a parsed simple command whose request carries a folder inside the bot's folder, and never a request that is opaque, whose text was cut, or that names no folder. The daemon never allows a cut request, on any level. The daemon declines on its own only what it cannot let run, each with its reason: a request with no allow-once option, a request whose record could not be written, and, in a review session, a tool that is not the daemon's. Every other request waits for a person, with no timer: a routine that needs an answer shows as waiting and skips its next occurrence. `approval.rs` decides from the floors, the rules, and the level, read from the bot's record at each request, at a change of level or rules (every waiting request is answered again), and when a person allows one (a refusal added since still wins); `approval/command.rs` reduces a command (the request's `rawInput.command`, a string or a list of arguments) to one simple command or `Opaque` (a pipe, a list, a redirection, an expansion, a glob, a subshell, `eval`, a cut target), decoding quotes and escapes as a shell does, and on Windows a command is simple only when the POSIX and the PowerShell readings agree. The floors (`approval/floors.rs`) read the command through `sudo`, `env`, `sh -c`, and the like: a recursive delete of a system folder or the home folder, any delete of the data folder, the database, or the daemon's program, `mkfs`, `dd` to a device, and a shutdown are declined (`Floor`); an opaque command that names one of their programs, or the program of a refuse rule, waits for a person on every level, and so does a command under a wrapper that moves it to another folder or root (`env -C`, `sudo -D`), whose relative paths the floors cannot read. A wrapper's options are read as `getopt` reads them, and an option the floors do not know makes the command opaque too. A relative path is read from both the request's folder and the bot's, and a floor that either reading reaches refuses: an agent that keeps its own folder between commands (Claude) can still run one elsewhere. A refuse rule matches the program by name and its arguments in order among the command's; an allow rule matches the program as written and leading arguments. The folder of a command comes only from where the profile says (`CommandFolder` in `provider/acp.rs`): no provider names one (`docs/harness-providers.md`, A9), so allow rules apply today only to an agent given with `--agent`, which names it as `rawInput.cwd`. Rules live in `approval_rules` (`store/rules.rs`) and travel as `ListApprovalRules`, `AddApprovalRule`, `DeleteApprovalRule`, and `ApprovalRules`. An allowed answer is committed to the database before the agent gets it; one that cannot be stored is declined as `NotRecorded`, and its turn ends as `TurnFailed`. The daemon treats a request as one for its own tool only when the request, or the tool call the agent sent under the same id, names the daemon's server in a field the agent sets and the model does not write, never by a title, and only for a tool the daemon serves (`daemon_tool` in `provider/acp.rs`). The daemon calls a tool's `run` only once the call may run: after the approval of an `External` tool.
- **A daemon tool declares one effect.** `Read`, `BotState` (a write to state the daemon versions and can put back: memory, skills), or `External` (anything else: a routine, a delegation, a script, a restore). The daemon allows an agent's request to call its own tool, then gates the call where it executes it: an `External` tool raises an ordinary approval request, to which the level and the rules apply. A tool runs only with a permit of the turn that runs (`TurnPermit`, `tools.rs`): no daemon tool runs between turns or once a stop is asked, and an agent's request for one is then cancelled. A `BotState` tool writes nothing itself: it returns a `Mutation`, which the conversation applies in its own loop only while the permit's turn still runs with no stop asked, in one transaction with the event it records. Skills and memory reach a provider through these tools only: the daemon writes no skill and no memory into a provider home. A provider that cannot call daemon tools in its mode that asks first runs without them, and its entry says so; no session mode is widened for them.
- **A turn the daemon starts needs the user's switch.** Every turn records its origin (`User`, `Routine`, `Review`, `Goal`, `Delegation`, `Retry`, `Budget`). Each bot has one switch per origin and a daily limit on daemon-started turns, counted in turns because ACP reports the size of the context and not the tokens spent: a turn whose switch is off or whose limit is reached does not start, and that is recorded. Every switch but `Retry` starts off and turns on only once the limit is set; no daemon tool changes a switch or a limit.
- **ACP stays at the edge.** ACP types do not leave the provider adapter, and MCP types do not leave the bridge module. Inside, the daemon records its own events (message, tool call, approval request).
- **GPUI source.** GPUI comes from Zed's git repository at a pinned rev, with Zed's `[patch.crates-io]` entries. Never use the crates.io `gpui`. The rev and the patches live in `crates/crowbot-desktop/Cargo.toml`; when the rev changes, copy the patch entries from Zed's `Cargo.toml` at that rev. One exception, for what GPUI cannot do on Linux: the client takes Zed's `gpui_wgpu` at the same rev from `crates/crowbot-desktop/patches/gpui_wgpu`, through a `[patch."https://github.com/zed-industries/zed"]` entry, with the changes recorded in `patches/gpui_wgpu.diff` (COLRv1 emoji, fallback families with no Latin glyph, emoji presentation). Only Linux builds that crate. Change GPUI there and nowhere else; after a change run `sh scripts/gpui-patches.sh diff`, after a rev bump `sh scripts/gpui-patches.sh refresh`, and `sh scripts/gpui-patches.sh check` must pass. `crates/crowbot-desktop/patches/README.md` says what each change does and where it stands upstream; a change Zed takes leaves the diff at the next rev bump. Any other GPUI defect is handled in the client, not by patching another GPUI crate (as `truncated.rs` does for a truncation that splits graphemes and `reduced_motion.rs` for the system's reduced motion).
- **Design contract.** UI work in the desktop client follows `DESIGN.md`: its tokens, its geometry rules (concentric radii; GPUI clips to rectangles, so no fill may reach a rounded corner), and its component contracts. A visual change that departs from it updates it in the same commit.
- **Visual checks and desktop control.** To look at the running client (a visual pass, a screenshot of a state) or to take control of the computer (click, type, drive a window), use the `/agent-desktop` skill. Do not use another automation tool for it. Never start or drive OpenBot with it: doing so started many processes and crashed the computer. Compare against screenshots of OpenBot that Arthur provides, and ask before the skill is used again in a session where he stopped it.
- **Reference projects.** OpenBot, Hermes Agent, and Zed are references for ideas: read them to learn how a problem was solved, then design the answer for this codebase. Never copy or translate OpenBot code or text; its license is noncommercial.

## Open decisions

- Full isolation of a bot from the user's `~/.claude`. The Claude profile already ignores the user's settings and instructions, but the bot still signs in with the user's credentials and writes its transcripts there. A daemon-owned `CLAUDE_CONFIG_DIR` would isolate both, at the price of one more sign-in. Codex and Grok already run that way: the user signs in to each once from Crow Bot.
- The Codex session mode. `read-only` is the only mode of `codex-acp` in which every write asks first; its sandbox also keeps shell commands from writing. Whether a bot on Full access should run Codex in a wider mode is not decided. US-001 of the harness PRD records what `read-only` allows for daemon tools.
- The remote transport. The protocol runs over any byte stream, but only the local endpoint exists: encryption and client sign-in for a daemon on a server are not designed.
- The Unix side of the endpoint is verified on Linux only. macOS is not verified.
- The transitions of the bot mascot. The mascot is drawn and alive (`DESIGN.md` 5.12): a crow's head seen from the front, in the bot's color, alone with no disc or background behind it, with a head the user picks, one beak for all, and eyes that show the bot's state. Its head sways, its eyes blink, and the dots of a bot that works hop; that state has no badge, and the states that ask for the user (waiting, failed, unread) keep theirs. The eyes change at once from a state to the next: that transition is not designed.
- Whether a native Rust client for the Claude CLI replaces `claude-agent-acp` later. If it does, it plugs in as an ACP agent, so the daemon does not change.
- An agent loop written in Rust in this repository, for API keys only (a subscription runs only through the provider's unmodified binary). It is the direction for what the harness cannot do from outside the loop: context compression, prompt caching, recovery from API errors. Its scope and its date belong to a later PRD; it plugs in as one more ACP agent.
- Whether a provider agent announces that it compacted its context. ACP version 1 names no such update. The harness PRD infers a compaction from a fall in the context size the agent reports and sends the core memory again; US-001 records whether each provider's size falls.
